# Translations of the headset UI

PLAN item 6.1. Only the in-headset panels (`ui/`) are covered here. The flat launcher is moonlight-qt
and has its own translations (its Language row); nothing here touches them.

## Adding a string (read this if `ui_i18n_gen` failed)

1. Add the `X(ID, "key", "English")` line to `ui/ui_strings.h` as before.
2. Add one line for its key to `MAP` in `tools/ui/gen_strings.py`, at the same place as in the header:
   `("native_my_key", NATIVE),` for a string written for this port (almost always). That is all: no
   regeneration, it shows in English in every language and in this file's TODO list.
3. Only when upstream Moonlight XR has the same string (same key, or same text under another key) use
   `SAME` or the upstream key instead, then regenerate (see "Regenerating" below; needs a shallow
   clone of upstream).
4. Rewording the English of a key whose `MAP` line is `SAME` or an alias also fails `ui_i18n_gen`
   ("the English of ... changed"): if it means something else now, make it `DRIFT`; then regenerate.
5. Run `ctest -R ui_i18n` (generator, tables, every panel in every language) before pushing.

## How a string reaches the headset

* Every word the panels draw is an id in `ui/ui_strings.h` (`UIS_*`), keyed by upstream's Android
  resource name, with its English text. The panels ask `ui_str(id)` at the moment they draw.
* The panels (`ui/panel_*.c`) are rasterised on the CPU at run time, through stb_truetype, from the
  bundled Noto Sans (`assets/fonts/`), into one RGBA atlas (`ui_atlas_rect`, `UI_ATLAS_W` x
  `UI_ATLAS_H`) that `xr/xr_assets.c` uploads to a single swapchain. The glyphs go through an 8-bit
  glyph cache (1024 x 1024, flushed when full) that holds only what is on screen.
* Nothing is pre-rendered at build time: there is no per-language atlas to build or ship. A second
  language costs its strings in the binary (about 2 KB of text and 1.5 KB of pointers each, 70 KB
  for all 19), and for Chinese, Japanese and Korean a system font loaded at start (below). The atlas
  stays the same size.

## Where the translations come from

`tools/ui/gen_strings.py` reads upstream Moonlight XR's
(github.com/Gilleece/moonlight-android-xr, GPLv3) `app/src/main/res/values/strings.xml` and each
`values-<lang>/strings.xml` and writes `ui/ui_strings_i18n.inc`, committed, so the build needs no
upstream checkout. Its `MAP` lists every key of `ui_strings.h` and where its translations come from:

* `SAME`: upstream has the key with the same meaning (104 keys).
* an upstream key: the same text under another name (5: Cancel, Close, Send, Back, Ray).
* `DRIFT`: upstream has the key, but this port's English now says something else (5: the
  "left View + grip" shortcut and toast, where upstream names the menu button; the About tab's
  report line and the report sheet's explanation and Save button, where upstream sends and this
  port saves). Upstream's translation would be wrong, so these stay English.
* `NATIVE`: written for this port, English until a person translates them (how many is in the
  generated part below).

So 111 keys are shared with upstream, as the PLAN counted; 104 of them are taken, plus the 5 aliases; two (the Ko-fi sheet lines) drifted when the sheet gained its Open page button.

Android's quoting and escapes are resolved (`\'`, `\"`, `\n`, `\uXXXX`, whitespace, markup),
numbered formats (`%1$s`) become plain C ones, and a translation whose values differ from the
English format (reordered, another type, a `%` where the English has none) stays English, so a
translated format can never take other arguments than the code passes.

Upstream's 19 complete languages are in. Left out: the languages upstream translated only for its
Android screens (13 of the headset's strings or fewer: Bulgarian, Greek, Hungarian, Indonesian,
European Portuguese, Romanian, Vietnamese, Esperanto, Latvian; the panels would be English with a
word here and there), Hebrew (right to left: the text drawing has no bidi), Tamil (needs shaping),
Persian and Kurdish (nothing translated).

At run time `ui_str` returns the chosen language's text, or the English where it has none
(`ui_str_lang`, `ui_str_translated`; language 0 is English).

### Regenerating

```sh
git clone --depth 1 https://github.com/Gilleece/moonlight-android-xr /tmp/upstream
tools/ui/gen_strings.py --res /tmp/upstream/app/src/main/res --upstream-rev "$(git -C /tmp/upstream rev-parse --short=12 HEAD)"
```

It rewrites `ui/ui_strings_i18n.inc` and the generated part of this file. `tools/ui/gen_strings.py
--verify` (run by the `ui_i18n_gen` test) needs no upstream: it checks that every key of
`ui_strings.h` has a `MAP` line and that the committed table was made from this `MAP`.

### Adding a string to `ui_strings.h`

Add a `MAP` line for it in `tools/ui/gen_strings.py`, in the same place: `NATIVE` for a string
written for this port (no regeneration needed), `SAME` or an upstream key when upstream has it
(regenerate). Without the line `ui_i18n_gen` fails and names the key. The keys of lanes not merged yet are listed
in `PENDING` already, so their merges need nothing here.

The generated table records a hash of the English each translated key had, and `--verify` fails when
one changes: a reworded string may no longer mean what the translations say. Decide, then regenerate:
`DRIFT` when it means something else now (wave6-kofi's "Not now" for `vr_kofi_close` will be one),
otherwise only regenerate.

### Translating a native string

A person who speaks the language writes `tools/ui/native/values-<dir>/strings.xml` in upstream's
format (`<string name="native_forget">...</string>`), with keys from `MAP`'s `NATIVE` and `DRIFT`
lines only, and regenerates. No translation here is made by a machine: an English fallback is
better than a guess, and the lists below are the work left.

## The setting

`[ui] language` in `config.ini` (`ui/settings.c`): `auto` (the default), `en`, or a setting code from
the table below (`pt_BR` as a locale spells it reads too). `auto` is the locale of the VR client's
process, `LC_ALL`, else `LC_MESSAGES`, else `LANG` (`ui_lang_from_env`): `pt_*` is Brazilian
Portuguese, `zh_TW`/`zh_HK`/`zh_MO` Traditional Chinese and other `zh_*` Simplified, `nn` and `no`
Norwegian Bokmål, `C`, `POSIX` and anything without a table English. `xr/xr_prefs.c` applies it at the
first `xrApplySettings` of the process (the session's start) and keeps it for the run, so every panel
is in one language; a change takes effect at the next start (one per stream from the flat launcher).
The old `[stream] language` that PLAN 1.6 dropped still reads as an unknown key.

The flat launcher's Settings page mirrors it as **Headset language** (MISC, under its own Language
row, `launcher/qml/XrSettingsView.qml` + `launcher/src/mlxrprefs.*`), and says that it applies at the
next start. There is no cog row: the tabs are full.

## Fonts

* Latin, Latin Extended, Cyrillic and Greek: the bundled Noto Sans 2.013 has every glyph the 15
  languages in those scripts use (`ui_lang_start` checks each string, `ui_i18n_panels` each panel).
* Chinese, Japanese, Korean: no font is bundled (Noto Sans CJK is 10 to 20 MB a weight). `text.c` has
  a fallback face, used for any code point the family lacks. `ui_font_find_cjk` looks under
  `/usr/share/fonts` (`$MLXR_SYSTEM_FONT_DIR` instead when set; four levels down) for, in order, a
  `NotoSansCJK-Regular.ttc` collection (Arch's and SteamOS's `noto-fonts-cjk`, Debian's
  `fonts-noto-cjk`) and its face for the region (JP, KR, SC, TC, picked by the face's name),
  `NotoSansCJK<region>-Regular.otf`, `NotoSans<region>-Regular.otf`, then another region's
  `NotoSansCJK` file (each has kana, hangul and the common Han), with the `-Medium` file beside it
  when there is one. The file is mapped, not read, so only the glyphs drawn are paged in. stb_truetype
  draws the CFF outlines.
* At start `ui_lang_start` loads it and checks that every string of the language has its glyphs.
  Without the font, or with a glyph missing, the language is English and the log says why
  (`UI language ja (日本語) needs Noto Sans CJK, which is not under /usr/share/fonts: English
  instead`). Whether the Frame's SteamOS image has `noto-fonts-cjk` is for the headset to confirm.
* The text is not shaped (no bidi, no Indic), which is why Hebrew and Tamil are left out.

## The overflow test

`tests/ui/test_i18n_panels.c` (`ui_i18n_panels`) draws 59 panel states (every cog tab and its
greyed, room, locked and 3D-off forms, the picker, both keyboards and their sheets, the bar, the exit
prompts, the hand hint, Ko-fi, the Host sheet and its confirmation, the report sheet, the toasts as
`xr_panels.c` makes them, the clock strip, the PC and app lists) in every language. `text.h`'s
`ui_text_set_trace` reports each text drawn with the box it inked, and each cut. A panel fails when a
text of the table is cut with an ellipsis, a glyph is missing, a text leaves the panel, is wider than
the cell, key, tab or button its middle is in (a greyed row's cells and a track's parts count as one
zone), runs into a cell it is not in, or overlaps another text (texts under a dialog are a layer of
their own). CJK runs where the system has the font and is reported as skipped otherwise; with
Debian's `fonts-noto-cjk` all four pass. The panels of de, fr, pl, ru and the CJK languages that
differ from the English ones are written to `build/ui/tests/i18n-panels/<code>/` and so are in CI's
`test-pictures` (`MLXR_I18N_PNGS=all` writes every language, `MLXR_I18N_ONLY=<code>` runs one). They
are not goldens: the golden procedure stays as it is, and the English panels it covers are unchanged.

What it found, and the fixes (English is drawn exactly as before): a settings row's label shrinks to
its room (down to 14 px from 22), short of the track or of the row's readout, as the cells' names
already did ("Чувствительность" ran into "8 px/°"); the Display tab's Mode row moves its shortcut line
down when the label reaches below the baseline (Russian, Polish, Finnish).

was translated in house, so most of it has not been read by a native speaker yet". The PC and app list
strings are Moonlight for Android's, from its translators on Weblate. Corrections belong upstream (its
`values-<lang>/strings.xml`), then a regeneration here.
