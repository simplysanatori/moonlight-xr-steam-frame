# Launcher lane report (lane/launcher)

A patched **moonlight-qt 6.1.0** (submodule `third_party/moonlight-qt`, tag v6.1.0 f786e94c, never edited in place)
whose stream start hands off to the native OpenXR client. Everything else in the flat UI is stock.

## Patches (what and why)
1. `0001` `app/app.pro`: build `mlxrhandoff.cpp/.h`.
2. `0002` `app/main.cpp`: own QSettings/cache profile "Moonlight XR Native" (org = app; `MLXR_LAUNCHER_PROFILE=Moonlight` selects Moonlight Qt's names); first-run import of the flatpak config; window title/display name "Moonlight XR Native", desktop file name `moonlight-xr-launcher` (was `com.moonlight_stream.Moonlight`, so the two apps do not share an app id); `MLXR_LAUNCHER_SELFTEST` hook.
3. `0003` `Session::exec()` calls new `Session::execVr()` when the hand-off is enabled (client found, `MLXR_HANDOFF` not 0); everything else in `Session` is untouched, so with no client installed (or `MLXR_HANDOFF=0`) the launcher streams flat exactly like stock. New signal `vrStreamStarted()`. `StreamSegue.qml`: connects it and sets the stock tip (below); after the stream, restarts polling if it idled out (the window is never hidden, so the app list refreshes). 
4. `0004` test hooks: `objectName: "stackView"` in main.qml and one call in main.cpp (env-driven, inert).

7. `0007` (lane artemis-settings) `app.pro` builds `mlxrprefs.cpp`; `qml.qrc` adds `gui/XrSettingsView.qml`; `main.cpp` registers the `MlxrPrefs` singleton; `main.qml`: the Settings button opens `settingsPageUrl()` = `XrSettingsView.qml` when `SystemProperties.nativeVrHandoff`, else stock `SettingsView.qml` (the version label shows on both); `AppView.qml`: Artemis's Quick Resume (a click or Enter on a running app resumes it at once when `MlxrPrefs.quickResume`; off by default = stock).

5. `0005` decoder capabilities in hand-off mode (smallest change): `Session::getDecoderInfo()` returns at once when the hand-off is enabled (hardware accelerated = yes, HDR = no, no resolution limit) instead of probing the local FFmpeg/SDL decoders, which the VR client never uses; this removes stock's startup "No functioning hardware accelerated video decoder was detected" dialog (it was visible in the first screenshots). New read-only property `SystemProperties.nativeVrHandoff`; `SettingsView.qml` drops the "AV1 (Experimental)" codec entry and disables "Enable YUV 4:4:4" (stock's own disabled tooltip "YUV 4:4:4 is not supported on this PC." applies); "Enable HDR" is disabled through stock's existing `supportsHdr` (tooltip "HDR streaming is not supported on this PC."). The VR client supports H.264 and HEVC 8-bit only. Stock has no other decoder-based gating: the codec list, 4:4:4 and the stream-start checks (`validateLaunch`, only in the SDL flow) are never reached or never greyed by stock outside the probe above. With the hand-off off (no client, `MLXR_HANDOFF=0`) all of this is stock again (verified: the probe runs and the dialog shows).
8. `0008` (lane launcher-return) `Session::execVr()` makes two calls into `mlxrhandoff.cpp`: `watchFlatWindow()` when the stream is handed off and `flatWindowReturn()` right after `sessionFinished`/`readyForDeletion`. The watch logs the flat window's visibility, exposure, activation, platform surface and its first frame after each show ("flat window ..." Qt Info lines). After the stream, in Game Mode (gamescope) only, it hides and shows the window again if it has not been exposed and drawn after 1 s, does so once more 2 s later, and asks Steam for the flat screen once more as soon as the window has drawn. On a desktop it only logs. Evidence and owner check: `launcher-return.md`.
9. `0009` (lane launcher2) `streamingpreferences.cpp/.h`: stock's `getDefaultBitrate` body moves, unchanged, into a static `stockDefaultBitrateMbps()` that returns the figure before stock rounds it to whole Mbps. New `StreamingPreferences::getHandoffDefaultBitrate()` (Q_INVOKABLE) = `MlxrHandoff::headsetDefaultBitrateKbps(stockMbps)`: twice that figure, rounded to the nearest 500 kbps, capped at 150000 (the Artemis page's slider maximum). `getDefaultBitrate()` returns it when `MlxrHandoff::enabled()`, else stock's `qRound(...) * 1000`. Every stock caller therefore follows: the saved-bitrate fallback in `StreamingPreferences::reload()`, the command line parser, `Session` (the YUV 4:4:4 fallback compare), and the page's reset when resolution, frame rate or 4:4:4 change (`resetBitrate()` in `XrSettingsView.qml`, the three places in stock's `SettingsView.qml`). The first-run seed in `mlxrhandoff.cpp` calls `getHandoffDefaultBitrate(2560, 1440, 90, false)` = 98000. Values: 1080p60 40000, 1080p90 49000, 1440p60 80000, 1440p72 87500, 1440p90 98000, 4K60 and 4K90 150000. A bitrate already saved in the owner's config is not touched.
10. `0010` (lane launcher2) `main.cpp`: `MlxrHandoff::applyGameModeScale()` before the `QGuiApplication` is created. In Game Mode (`XDG_CURRENT_DESKTOP=gamescope`) and unless `MLXR_HANDOFF=0` it sets `QT_SCALE_FACTOR` to 1.5, or to `MLXR_LAUNCHER_SCALE` (a number, clamped to 1.0..2.5; junk gives 1.5). A `QT_SCALE_FACTOR` already in the environment is kept unless `MLXR_LAUNCHER_SCALE` is set. On a desktop nothing is set. The VR client's environment has `QT_SCALE_FACTOR` removed (`mlxrhandoff.cpp`, with the other variables the launcher keeps from it).
11. `0011` (lane launcher2) `main.qml`: the Help button opens `https://github.com/simplysanatori/moonlight-xr-steam-frame#readme` when `SystemProperties.nativeVrHandoff`, else stock's Setup-Guide. The other help links (decoder dialogs, gamepad mapping, the PC list's dialog) are stock.

## Hand-off contract
Pairing: before each launch `exportPairing()` writes, into `$MLXR_CONFIG_DIR` (default `~/.config/moonlight-xr`, the native client's dir): `client.pem`/`client.key`/`uniqueid` (the launcher's identity; if a different identity was there it is kept as `*.bak-<stamp>`), `servercerts/<uuid>.pem` (the pinned server cert from the live computer object) and the `hosts.ini` record (name, the address that answers now first, then manual/local/remote/IPv6 as extra addresses, MAC, ports; other hosts in the file are kept). This runs in-process from the computer Moonlight just talked to, so it is exact and needs no Python or timing against QSettings writes.

argv: `<client> --host <uuid> --app <id> --mode WxHxFPS [--bitrate KBPS] [--h264] [--sw-decode] [--audio 51|71] [--packet-size N] [Artemis page flags, below] --exit-to-caller` (+ `MLXR_LAUNCHER_EXTRA_ARGS`). Mapping: width/height/fps/bitrate as set in Moonlight's Settings; "Force H.264" -> `--h264` (auto, HEVC and AV1 leave the client's own HEVC/H.264 choice; AV1, HDR, YUV 4:4:4 are not supported by the client); "Force software decoding" -> `--sw-decode`; audio 5.1/7.1 -> `--audio`; packet size -> `--packet-size` (also "treat as local", as Moonlight does). Not mapped (flat-window only or unsupported): window mode, V-Sync, frame pacing, HDR, 4:4:4, game optimizations (SOPS), play audio on host, multi-controller, quit-app-after (the client always ends the host session on the bar's Exit), mouse/gamepad options (VR cog and the pad lane own those).

env of the child: inherited minus `LD_LIBRARY_PATH`, `MESA_GL(SL)_VERSION_OVERRIDE`, `QSG_RENDER_LOOP`, `QML_DISK_CACHE_PATH`, `SDL_VIDEODRIVER`, `SDL_VIDEO_*_WMCLASS`; cwd = the client's directory (assets are found relative to it); `PR_SET_PDEATHSIG=SIGTERM` so it never outlives the launcher; output (stdout+stderr) is written to `moonlight-console.log` (`$MLXR_LOG_DIR`, default `~/Games/MoonlightXRNative`).

Exit codes (`app/main.c`, with `--exit-to-caller` the message is one stderr line `MLXR_ERROR: <text>`, shown in Moonlight's own error dialog):
0 normal (the bar's Exit: host session ended; SteamVR quit; `--seconds`), 1 VR session could not start / unclassified, 2 usage, 3 host unreachable, 4 no such paired host, 5 no such app, 6 host refused the launch or the stream would not connect, 10 stream ended by itself (host closed it or network lost; dialog shown), **11 left with the disconnect chord: not an error, no dialog, the host's session keeps running**. A crash by signal gives "The VR client crashed. See moonlight-console.log"; a code without a message gives "The VR client stopped with code N".
After exit 11 (or 0) the launcher does nothing special: the window was never hidden, polling continues/restarts, and the app grid shows the running app with Resume / Quit through Moonlight's own polling, exactly as stock after a disconnect (stock returns to the same view). Quitting the launcher during a stream sends the client SIGTERM, which ends the stream like SteamVR quitting does.
CLI: `moonlight-xr-launcher stream <host> <app>` is stock's (CliStartStreamSegue -> Session -> hand-off, `quitAfter` quits the launcher afterwards); `pair`, `list`, `quit` untouched. Debug: `MLXR_LAUNCHER_DRYRUN=1` prints `MLXR_LAUNCHER_DRYRUN: <exact command line>` (also appended to `$MLXR_LAUNCHER_DRYRUN_OUT`) instead of running it (`=fail:CODE:message` plays a failing client); `MLXR_LAUNCHER_HIDE_WINDOW=1` hides the Qt window during the stream like stock's SDL flow; `MLXR_NATIVE_CLIENT` overrides the client path.

## Artemis-style Settings page (lane artemis-settings)
In hand-off mode the Settings button opens `XrSettingsView.qml`: first a Connection category (Network connection, the owner's), then Artemis's (ClassicOldSong/moonlight-android, `res/xml/preferences.xml`) categories in its order (Video, Audio, Gamepad, Input, Host, General, UI, Performance Monitor, Advanced, MISC), a title, the current value and Artemis's summary per row, lists in a radio dialog, seekbars inline, text entries in a dialog. With the hand-off off (`MLXR_HANDOFF=0` or no client) the stock page is shown, unchanged. Every row shown works; a row that cannot is greyed with "Not available: <reason>". Values live in three places, so old configs keep working: the stock keys of `Moonlight XR Native.conf` (resolution, fps, bitrate, codec, audio, host options, language, UI mode, decoder), new keys `mlxr/...` (+ `networkPath`) in the same file, and the VR client's `~/.config/moonlight-xr/config.ini` (edited in place: only a key changed on the page is rewritten, the commented default line is replaced, everything else stays byte for byte; checked with the client's own parser, `mlxr-settings-dump`). Flags are passed only when the value differs from the VR client's default, except `--fps match` (Match headset, the default refresh rate), which an untouched page adds.

The owner's host is **Apollo** (it reports Sunshine 7.1.431; Apollo is told apart, as Artemis does, by `<VirtualDisplayCapable>`/`<Permission>` in serverinfo). Read-only checks against it (2026-10-11, `mlxr-cli serverinfo` / `mlxr-cli clipboard`): virtual display capable and driver ready, permission 0x07131f00 (keyboard, mouse, controller, clipboard set/read, server commands, list/view/launch), one server command ("Bubbles"); `actions/clipboard` answers 403 "not in a stream", i.e. the endpoint and permission are there and it only works during a stream (Apollo `nvhttp.cpp getClipboard`), which is why the VR client does the clipboard requests. Launch fields as Apollo parses them (`nvhttp.cpp make_launch_session`): `virtualDisplay`, `scaleFactor` (default 100), `mode`'s rate below 1000 is multiplied by 1000 (Artemis sends fps*1000 for a fractional rate).

## Config and pairing sharing
Own profile `~/.config/Moonlight XR Native/Moonlight XR Native.conf` (cache `~/.cache/Moonlight XR Native/`). On the first run only (file absent), if the flatpak's `~/.var/app/com.moonlight_stream.Moonlight/config/Moonlight Game Streaming Project/Moonlight.conf` exists (else the native `~/.config/Moonlight Game Streaming Project/Moonlight.conf`; `MLXR_SEED_CONF` overrides, `MLXR_NO_SEED=1` disables) it is **copied whole** (client certificate + key + unique id, every PC with addresses, MAC, pinned server certificate and app list, all settings), read-only on the source; then these keys are rewritten for the headset: `width=2560 height=1440 fps=90 bitrate=98000 (lane launcher2: the hand-off default rule at 1440p90, was 80000) hdr=false yuv444=false videocfg=0 audiocfg=0 packetsize=0` and `mlxr/seeded_from=<path>` is added (the owner's flatpak has 1080p144 31 Mbps, chosen for a flat window). The user changes them in Settings as usual. Box-art cache is not copied (re-fetched from the hosts). Because the launcher keeps the same identity as the flatpak and as the earlier `seed-from-moonlight-qt.sh` import, the PC needs no re-pairing, and pairing done in the launcher works for the VR client at once.

## User-visible differences from stock moonlight-qt 6.1.0 (complete list)
1. Window title / app name: "Moonlight XR Native" instead of "Moonlight"; window class / desktop file name `moonlight-xr-launcher`; config and cache live under that name (above).
2. When a stream starts and the native client is installed, the stock StreamSegue stays up ("Starting <app>..." and spinner, stock text) and only the tip line changes to stock's wording with the new chord: **"Tip: Press Start+Select+L1+R1 to disconnect your session"** (strings: `qsTr("Tip:")`, `qsTr("Press %1 to disconnect your session")`, `qsTr("Start+Select+L1+R1")`). As stock, with no gamepad connected it reads **"Tip: Press Ctrl+Alt+Shift+Q to disconnect your session"** (stock's `qsTr("Ctrl+Alt+Shift+Q")`); the VR client takes that combo from a physical keyboard since 2026-10-10. The wrapper `moonlight-xr-launcher.sh` sets `MLXR_LAUNCHER_HIDE_WINDOW=1` (its default), so the window is hidden once the VR client prints `MLXR_STREAMING`, as stock hides it when its SDL window opens, and shown again by stock's `sessionFinished` handler; `MLXR_LAUNCHER_HIDE_WINDOW=0` keeps it up.
3. The hand-off's failures use the stock error dialog with the client's message (new texts: "The host is unreachable...", "The VR client stopped with code N...", "The stream ended: the host closed the session or the connection was lost", pairing export errors).
4. Streaming is done by the VR client: stock's SDL stream window, its decoder checks and `quitAppAfter` do not apply while the client is installed.
5. In hand-off mode only: no startup hardware-decoder warning; the Settings "Video codec" list has no AV1 entry; "Enable HDR" and "Enable YUV 4:4:4" are disabled (greyed, with stock's "not supported on this PC" tooltips). Reason: the VR client decodes H.264/HEVC 8-bit 4:2:0 on the V4L2 hardware decoder, and the local SDL/FFmpeg probe is about a stream this process no longer runs.
6b. (lane artemis-settings) In hand-off mode the Settings page is the Artemis-style page (section above), not stock's; Quick Resume (off by default) changes what a click on a running app does. With the hand-off off everything is stock (the stock comparison still gives 0 px on Settings).
7. (lane launcher-return) After a stream in Game Mode (gamescope) only: Steam is asked to show the game's flat screen in the SteamVR dashboard (0, 1 and 2.5 s after the VR client exits, and once the window has drawn again; `steam_cef.py`), and the window is hidden and shown again when it has not been exposed and drawn within 1 s (once more 2 s later). On a desktop nothing changes apart from the "flat window ..." log lines.
8. (lane launcher2) Hand-off mode only: the default video bitrate is twice stock's for the same resolution and frame rate (rounded to 500 kbps, at most 150 Mbps), wherever stock uses its default: first run (98 Mbps at 1440p90), the Settings page's reset when resolution or frame rate changes, the Session 4:4:4 fallback, the command line. In Game Mode the flat UI is drawn 1.5 times larger (`MLXR_LAUNCHER_SCALE`, 1.0 to 2.5; `QT_SCALE_FACTOR`). The Help button opens this project's readme. With `MLXR_HANDOFF=0`, or on a desktop for the scale, all three are stock.
